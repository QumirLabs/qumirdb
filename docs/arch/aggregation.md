# Aggregation architecture

Aggregation combines query-specific key and reducer operations with reusable
oz-lang table algorithms.

## Overview

Aggregation is a pipeline breaker. It consumes every input `TRowSet`, updates a
query-local hash table, then emits one dense output `TRowSet`.

The implementation is deliberately split into three layers:

1. C++ derives concrete query types and generates query-specific Qumir AST.
2. Reusable Oz code implements the generic hash table and lifecycle with
   function-level generic type parameters such as `[Key]`.
3. C++ owns execution and state lifetime; Oz code allocates/frees internal
   table storage and materializes owned result buffers.

There is no C++ implementation of the aggregation algorithm. C++ composes and
JIT-compiles Oz plus generated AST into two named functions:

```text
agg_dispatch(ht, batch, arg, op) -> i64
agg_finish_rowset(ht, output) -> i64
```

## Planning and compilation

`TAggregateOperator` stores group column names and `TAggregateSpec` entries.
The physical planner builds its input node, computes the post-pruning input
schema, and calls:

```cpp
TKernelCompiler::CompileAggregate(inputType, groupKeys, aggs)
```

Compilation performs these steps:

1. Validate group columns and aggregate specifications.
2. Build a `TAggregateKeyDescriptor` for the concrete group key.
3. Obtain the external `TColumn`, `TRowSet`, and `HashTable` types from
   `QumirDbModule`.
4. Generate key hash/equality and ownership helpers, plus typed reducers.
5. Compose update, lifecycle, and finalization in one program with explicit
   named entrypoints.
6. Finalize it with the other query kernels and retain the shared code owner
   for as long as any dispatch can invoke it.

A scalar key uses its concrete type; a composite key uses a generated struct.
String lookup keys borrow batch bytes, while stored keys own their bytes.
The generic table is specialized to these representations by Qumir.

## Building the update AST

The aggregate generator constructs one top-level Qumir block in
dependency order:

```text
optional generated Key type declaration
generated rh_hash(Key)
generated rh_key_equal(Key, Key)
generated reduce_0 ... reduce_N
generated agg_apply_reducers(...)
generic control-byte lookup, rehash, and update helpers
owned-key arena and output helpers
generated agg_dispatch(...) and agg_finish_rowset(...)
```

The complete block is unresolved when returned. `TLLVMRunner` resolves it with
`AllowOverloads=true`, instantiates generic named types, lowers it, and compiles
the explicitly named update and finalization entries.

The generated dispatch wrapper adapts `TRowSet` to the generic table API:

- reads each key column through its concrete pointer type;
- materializes a generated struct value for a composite key;
- reads each aggregate argument with its concrete type and validity;
- respects `TRowSet.Selection` when it is non-null;
- calls `aht_update(ht, key, value)` once per selected row.

## Generic hash injection

The Oz table never knows how a key is hashed or compared. It only contains
calls with these names:

```text
rh_hash(Key) -> i64
rh_key_equal(Key, Key) -> bool
```

The concrete overloads are generated by `GenKeyOperationFunDecls` from the
`TAggregateKeyDescriptor` and inserted before the generic Oz library in the
same AST. They do not come from a fixed `key_ops_i64.oz` production dependency.

Specialization works as follows:

1. Generic Oz functions declare function-level type parameters, for example
   `(fun aht_update [Key] ((var ht <ref HashTable>) (var key Key) ...) ...)`.
2. Generated `agg_dispatch` calls `aht_update` with the concrete key value.
3. Qumir infers generic type parameter `Key` from the call and instantiates the
   generic function chain.
4. Calls to `rh_hash` and `rh_key_equal` resolve to the generated concrete
   overloads in the merged AST.

This is why `AllowOverloads=true` and compilation of the complete merged AST
are required. The generic libraries and concrete type helpers are not compiled
independently and linked afterward.

### Generated hash rules

The generator recursively walks the AST type rather than the raw memory:

- integers are converted through the corresponding unsigned width, widened to
  `u64`, and mixed with the xorshift/multiply sequence used by the project;
- `f64` uses `qdb_f64_bits`, canonicalizes `+0.0` and `-0.0` to the same bits,
  canonicalizes every NaN payload to one quiet NaN, then uses the same mixer;
- structs hash every field recursively and combine field hashes in declaration
  order with a boost-style ordered combiner.

Equality follows the same recursive type walk. Integer leaves use ordinary
equality. `f64` compares canonicalized bits, so all NaNs are equal for hash-key
purposes and signed zeroes are equal. Struct equality is the conjunction of
all field equalities.

The invariant is strict: if `rh_key_equal(a, b)` is true, both values must have
the same `rh_hash` result.

## Reducer injection

Reducers are query-specific generated functions for `count`, `sum`, `min`, and
`max`. Their state and arguments use the appropriate types, including nullable,
string and boolean values. Each selected row updates the reducer slots for its group:

```text
lookup group -> dense group slot -> update each reducer -> finalize values
```

The generated reducer application calls concrete operations statically; the
generic table does not dispatch on aggregate function names at runtime.
`count(*)` counts rows; `count(arg)` skips NULLs. Other reducers track validity
so an all-NULL contribution is distinguishable from a numeric zero.

## Global aggregate identity

A SQL aggregate without grouping has one group even when its input has no rows.
The logical plan carries this property explicitly; a constant grouping expression
in an ordinary `GROUP BY` does not have it. The generated initialization creates
the global group without applying a reducer update. Its COUNT states are zero,
and other reducers remain invalid until a non-NULL value contributes, so empty
SUM, MIN, MAX, and AVG produce NULL even for non-nullable input columns.

In a parallel global cascade, each partial aggregate owns this identity group.
The combine stage merges their rows with the usual reducers. It does not create
an additional identity contribution or count the seeded groups as input rows.
A SUM that merges partial COUNT states preserves COUNT's zero identity; an
ordinary SQL SUM remains NULL over an empty global input.

The empty grouping set of ROLLUP and CUBE (the grand total) has the same property.
Grouping sets share one table keyed by the set index followed by the group keys, so
its group is the key `(index, NULL, ...)`. The generated initialization seeds it for
every empty set, in each partial aggregate of a parallel cascade as well. The
combine stage then needs no special case, and ROLLUP over an empty input returns the
grand-total row, as `SELECT count(*)` does.

## Hash table

An aggregate task keeps its groups in one of two layouts. Both live in the same
table state and are served by the same compiled program, so a task can
start in either and move from the first to the second while it runs.

### Swiss table

The swiss table uses Swiss-style grouped control-byte probing. It separates
probe storage from dense output storage:

```text
probe slot: key, control byte, stable dense slot id
dense slot: group key, reducer states
```

A short hash fingerprint in each control byte identifies candidate slots. Full
key equality is evaluated only for candidates. An empty slot ends an unsuccessful
probe; the group matcher has portable and target-specific implementations.
See Abseil's [Swiss Tables design notes](https://abseil.io/about/design/swisstables)
for the metadata-filtering idea. QDB implements its own typed Oz table.

Probe-table growth preserves stable dense group ids, so rebuilding lookup slots
does not reassign reducer state. Before a new group exceeds the current 7/8
load threshold, the table grows and rehashes keys. Group NDV estimates can
pre-size it, but missing or inaccurate statistics still require normal growth.

Every state word of a group, one per reducer and more for a nullable or
decimal one, lives in its own array. An update therefore reads the control
bytes, the stored key, the slot's dense group id and one array per state word,
each read depending on the one before. While the table fits in the
cache, that is cheap; beyond it, each array costs a cache miss of its own.

### Row layout

The row layout keeps a group in one row, as an array of structs, instead of a
structure of arrays. Richter, Alvarez and Dittrich compare the two for linear
probing ([PVLDB 9(3), 2015, Section 7](https://doi.org/10.14778/2850583.2850585)):
an array of structs touches fewer cache lines while probe sequences are short,
because a successful probe finds the key and its value in one cache line where
a structure of arrays reads at least two. In their measurements, on a table far
larger than the caches, it was faster for insertions, and for lookups at low
load factors with few unsuccessful lookups. The aggregate probes in that
regime: its entries stay at most half full, and every lookup finds its group or
inserts it.

QDB builds the layout on the row table that the row join also uses: rows in an
arena of fixed-size blocks, indexed by 8-byte entries that hold a 16-bit salt
from the key's hash above a 48-bit row pointer, with linear probing at a load
of at most one half.

```text
row:   hash | key | state words, in the order of the swiss table's arrays
entry: salt (16 bits) | row pointer (48 bits)
```

An update reads one entry and one row, about two cache lines, whatever the
number of states. A batch is processed in chunks of rows and passes over each
chunk, so the cache misses of different rows overlap, as in the group
prefetching of Chen, Ailamaki, Gibbons and Mowry
([ICDE 2004](https://doi.org/10.1109/ICDE.2004.1319989)); here the processor
overlaps them without prefetch instructions:

1. Compute the key and hash of every selected row.
2. Walk every row from its home entry to the first entry that is empty or
   carries its salt.
3. Read that entry again and compare keys there, or insert at an empty entry.
   An earlier row of the chunk may have inserted there since the walk. Rows
   with equal keys walk the same entries, so the first of them inserts the
   group and the others find it. A row whose candidate holds another key moves
   on and walks again in the next round.
4. Apply every row to the states of its group; the row that inserted a group
   starts from zero states, as the swiss table's new group does.

Only a row that stands at an empty entry can insert, and only one group, so
the entries grow before a round in which those rows could fill more than half
of them. Growth rewrites only the entries, from the hashes kept in the rows;
the rows do not move. Finalization scans the arena.

The row layout serves fixed-width keys and states: integers, dates, decimals,
`f64` and booleans, alone or together, with COUNT, SUM, MIN, MAX and the AVG
built from them. A string key or reducer, and the groups that a global
aggregate or an empty grouping set has over an empty input, keep the swiss
table. The browser runtime uses the swiss table only.

### Choosing the layout

A task starts as a swiss table and moves to rows once it is large enough for
rows to pay. An estimate never starts a task in rows, because an estimate that is
too high would leave a small table in a layout that costs up to twice as much per
row while it fits in the cache.

- With S state words per group and rows of R bytes, rows are faster from a table
  of about 8 MiB / S^1.5 bytes (groups * R >= 8 MiB / S^1.5). The bound G is that
  number of groups. The swiss table starts with at most the slots whose 7/8 load
  holds G groups, so it has to grow, and rehash, exactly when it reaches G.
- At that rehash the table moves to rows. The rehash would rewrite the table
  anyway, so the move costs about as much: the groups move in their dense order
  and the rest of the batch continues in rows. There is no move back.
- The estimate of the groups of the task sizes the entries of the move, up to
  what a swiss table within the memory budget of the pre-sizing would hold, so a
  large table does not rebuild its entries many times and a grossly overrated
  estimate cannot allocate more than the swiss table would have. Without an
  estimate the entries are sized for twice the groups moved.
- An aggregate without state words, such as DISTINCT or the deduplication of
  COUNT(DISTINCT x), stays in the swiss table: it has no state arrays whose reads
  the row would save.

The bound comes from a microbenchmark of both layouts with one task per
worker, as a parallel aggregate runs: the row layout became faster at about
8 MiB of rows with one state word, 3 MiB with two and 1 to 1.5 MiB with four,
and at every size with eight, for one- and two-column integer keys alike. The
swiss table reads one more array for every state word, and its cost per row
grows the fastest as the table leaves the cache. A table that stays below the
bound never pays for the row layout.

Partial and final aggregates and the hash shuffle between them work as before;
each task owns one table and chooses its layout by itself. The settings that
force a layout and the diagnostics that show the choice are described in the
[wiki](https://github.com/QumirLabs/qumirdb/wiki/Adaptive-aggregate-hash-table#settings-and-diagnostics).

## Finalization

Finalization is part of the same generated program as update. It turns dense
group storage into a normal columnar `TRowSet`:

1. Measure output sizes, including variable-width string bytes.
2. Allocate column buffers, offsets, and validity storage.
3. Project scalar/composite keys and reducer values into those columns.
4. Destroy table storage after output has acquired independent ownership.

String keys are copied out of the table arena; output cannot borrow bytes from
a table that is about to be destroyed. The result owner releases its buffers
when downstream consumers finish with the batch.

## Runtime execution

The aggregate processor follows this lifecycle:

```text
initialize state
  -> for each input batch: update selected rows
  -> at EOF: finalize one dense result batch and destroy table state
  -> publish result, then report completion
```

Initialization is deferred until the first use, allowing physical lowering to
create state before kernel finalization. If execution stops early, destruction
also releases initialized state and any pending output.

## Partial aggregate plan

The threaded scheduler has two plans for a grouped aggregate. The first plan
sends raw rows to partitions. Each partition then builds complete groups:

```text
input[N] -> repartition(group keys, N -> P) -> aggregate(single)[P]
```

The second plan uses a local aggregate before the exchange. The scheduler uses
this plan when table statistics show a large drop in the row count:

```text
input[N]
  -> one-to-one
  -> aggregate(partial)[N]
  -> repartition(group keys, N -> P)
  -> aggregate(final)[P]
```

Each input lane owns one hash table. Each destination partition also owns one
hash table. All lanes in one phase use the same compiled kernel. The final
phase reads rows from the partial phase. `BuildAggregateCombineOperator` builds
the final aggregate. It changes `count` to `sum`. It keeps `sum`, `min`, and
`max` as they are. Each function reads its own partial output column.

The scheduler uses the second plan whenever statistics do not rule it out. It
needs a parallel input, a normal `GROUP BY` and at least 1,048,576 estimated
input rows. Statistics then only argue against the plan. The groups of a
composite key are at least as many as the values of any one key, so a key with
more than one eighth as many values as rows settles it: there is too little to
reduce. An estimate of the groups below that bound keeps the first plan too when
it promises fewer than 8x fewer groups than rows. Without an estimate (a
computed key has no NDV), or with the trivial bound of a composite key (the
product of the key NDVs under independence that already reaches the row count
holds for every input and says nothing about the groups), the partial phase
decides at run time, as the next section describes. The setting
`[aggregate] partial = false` turns the second plan off for tests and
diagnostics. A global aggregate uses its `partial -> gather -> final` plan only
with `[aggregate] cascade_global = true`. SQL grouping sets always use their
special two-phase plan.

### Adaptive partial phase

A partial table reduces rows only as far as the lane's data allows: a key with
few repetitions per lane sends almost every row on anyway, after paying for a
hash insert and a table the size of the lane. The partial phase therefore
follows the bounded-memory partial preaggregation of Larson
([ICDE 2002](https://doi.org/10.1109/ICDE.2002.994787)): it is a table of
bounded size that absorbs what it can and emits the rest, and the final phase
completes the groups whatever the partial phase emitted.

Each lane watches its own reduction. After `[aggregate] partial_sample_rows`
input rows it compares the rows it hashed with the groups it produced, the
emitted groups included. A group holds `rows / groups` rows on average; when
that falls below `[aggregate] partial_min_reduction_factor`, the same 8x the
plan asks of an estimate, hashing does not pay for itself: the exchange moves
the group anyway and the final table hashes it again, and with string keys the
partial insert and its emission copy every new key twice more, so a group has to
absorb several rows to pay for them (ClickBench q17 loses a third of its time
to a partial phase that reduces 4x per lane). The lane then emits its table and hands the remaining batches through as
single-row partial states, which a generated projection produces: the keys as
they are, `1` for `count(*)`, `1` or `0` by `qdb_is_null` for `count(x)`, and
the argument of `sum`, `min` and `max` widened to the state type. The final
phase cannot tell these rows from emitted groups. Switching strategy on the
observed ratio of distinct keys to rows follows the hybrid aggregation of Müller
et al. ([SIGMOD 2015](https://doi.org/10.1145/2723372.2747644)), who switch
between hashing and partitioning on the same signal. The decision is one-way:
a lane that passes rows through never hashes again.

When the table reaches `[aggregate] partial_max_groups` groups it emits them and
restarts empty, so a lane's memory is bounded however many groups its input
holds. The emitted groups count towards the lane's reduction, so a lane that
keeps emptying its table is judged by the rows it actually saved. A partial
aggregate whose projection cannot be built keeps the bounded table and never
passes rows through; the results are the same either way.

Passing rows through is not free: the lane hashed its sample, and a state row is
wider than the input row it stands for (a `count` adds eight bytes). That is why
statistics that already show too little reduction keep the first plan instead of
leaving the decision to the partial phase.

Partial and final aggregates have distinct executable stage ids and explicit
`EAggregatePhase::Partial` and `EAggregatePhase::Final` values. The
`THashShuffleConnection` between them has a `TRepartitionSpec`. This spec has
the group keys. The connection also has source and destination lane counts.

This connection is the border for a distributed scheduler. Such a scheduler
can put the two phases on different workers. It can replace the local
many-to-many connection with a network connection. It does not need to change
the aggregate rules or read keys from debug names. The common planner helper
owns the combine rule, so both local and distributed schedulers can use it.

A two-phase `f64` sum changes the addition order. Its result is valid, but its
last bits can differ from the result of the first plan. Integer functions and
`min`/`max` do not have this effect.

## Current constraints

- A group-key descriptor is required; global aggregates use a synthetic key.
- Aggregate arguments at this boundary are column references; planning
  materializes computed arguments first.
- Built-in reducer kernels implement `count`, `sum`, `min`, and `max`; planning
  expresses `avg` using `sum` and `count` of its argument, and `bool_and`
  (`every`) and `bool_or` as `min` and `max` of a BOOLEAN (FALSE < TRUE).
- String and nullable keys are supported. Matching key equality and hashing,
  plus owned storage for retained strings, are required for every key type.
